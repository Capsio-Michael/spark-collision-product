# 火花来源与碰撞路径：交互与引擎对接增补

状态：前端已实现；以下为待引擎方确认的可选响应扩展，不代表真实分析引擎已经支持。沿用现有项目、总览、认知详情与证据接口，无新增项目或独立网站。

## 用户看到什么

- 橙色单火花：同一场对话内的追问或反例改变了判断。
- 紫色双火花：不同场次的信息共同改变了判断。
- 灰色空心圆：待验证线索，尚未形成认知突破。
- 关键事实正常展示，不强行包装成火花。
- 新增印证保留已有火花颜色；颜色不表示可信度、确认或行动批准。
- 首页可以按单场、跨场筛选；点击“查看碰撞路径”进入现有详情，查看每次变化与各场贡献，点击 E 编号核查原文。

## 场次口径

“场次”是一次访谈、会议或有明确边界的讨论。转写、白板、纪要可能属于同一场次；一次导入多份文件不表示多场。同名参与者、相同日期或相同主题不能作为自动合并依据。

场次 ID 在项目内稳定，分组由用户明确提供或可靠来源元数据确认。分组不确定时，暂不返回可分类碰撞，不能让模型猜测归属。单份包含多场合并转写的材料应先拆成各场记录；本增补暂不支持一份 record 同时归属多个场次。

导入窗口由其他协作者负责。本次没有改变导入 POST 字段、自动给现有文件分组或迁移用户草稿。若引擎尚无场次来源，需要双方先补齐导入的分组能力；前端在此之前显示“碰撞来源待补充”。

## 响应扩展

`InsightSummary` 与 `InsightDetail` 增加可选的 `spark`。缺省或 null 兼容旧接口，前端保留原判断、条件、分歧和原文，不推测橙色或紫色。错误的扩展字段只降级火花区域，不使现有分析不可读。

比赛材料规模较小，第一版总览与详情返回相同的 spark 内容，以保证筛选、计数、详情口径一致。总览的 evidence 目录、详情的 evidence 数组均需包含路径所有引用，包括历史起点和新增印证，不能只返回当前判断的引用。

### Spark

| 字段 | 约定 |
| --- | --- |
| status | `collision` / `clue` / `observation` |
| reason | clue 必填，解释仍缺什么；不把潜在线索标成已实现突破 |
| conversations | 场次数组，collision 至少一项 |
| events | 按因果与产生顺序排列；clue、observation 为空数组 |
| latest_event_id | collision 必填，必须是 events 最后一项 ID |

### Conversation

| 字段 | 约定 |
| --- | --- |
| id | 稳定场次 ID，不采用文件数量或文件名临时推断 |
| title | 可显示的场次名称，必填 |
| date | 来源明确的日期，未知用 null，不使用导入时间冒充 |
| record_ids | 本场次关联材料 ID，非空且不重复；同一材料不可归入两场 |

### SparkEvent

| 字段 | 约定 |
| --- | --- |
| id | 稳定事件 ID，不能在后续快照中改写原事件 |
| version | 本事件首次保存的正整数快照版本；不能晚于当前读取版本 |
| kind | `collision` 或 `corroboration` |
| scope | collision 使用 `single` / `cross`；corroboration 使用 null |
| previous_event_id | 第一个事件为 null，其余指向前一事件；保留最初的橙色起点 |
| conversation_ids | 本事件实际贡献场次 ID；single 恰好一场，cross 至少两场；不能把所有覆盖场次塞进来 |
| before / after | 非空的变化前后判断；collision 必须不同；后项 before 必须承接前项 after |
| reason | 解释什么信息改变判断，或为何本次仅增加印证 |
| contributions | 每个参与场次一项，字段为 conversation_id、text、evidence_ids；与 conversation_ids 一一对应 |

每项贡献至少有一条可定位证据，引用的 record_id 必须属于该场次，quote 和 segment_id 必须存在。原文展示继续通过现有材料 GET 核对段落及原话，不因收到碰撞标注就跳过引用核查。

corroboration 不改变判断：before、after 必须相同并承接前项 after；不能成为第一项事件。界面采用最近一项 collision 的颜色，单场火花不会因为别的访谈重复认可就变紫。

### 合成示例：单场事件

```json
{
  "status": "collision",
  "latest_event_id": "spark_baseline_single",
  "conversations": [{
    "id": "conv_pricing", "title": "报价流程走查", "date": "2026-10-17",
    "record_ids": ["rec_02"]
  }],
  "events": [{
    "id": "spark_baseline_single", "version": 2,
    "kind": "collision", "scope": "single", "previous_event_id": null,
    "conversation_ids": ["conv_pricing"],
    "before": "先优化报价生成速度。",
    "after": "先拆分处理与等待时间建立基线，再决定优化哪一段。",
    "reason": "原有优化计划遇到尚未统计的等待，投入顺序转向先测量。",
    "contributions": [{
      "conversation_id": "conv_pricing",
      "text": "原有优化计划与未统计的等待并存，需要先分清时间消耗。",
      "evidence_ids": ["ev_07", "ev_03"]
    }]
  }]
}
```

跨场完整示例见 `frontend/src/fixtures/sparks.js`：单场起点 → 跨场细化 → 新增印证，全部为手工编写的合成演示。

## 版本、纠错与统计

- 仅展示所选快照已经存在的事件。不可用最新事件补齐历史快照；v1 的初步愿望不借用 v2 的来源。
- 同一个分析快照可以保存多项事件，事件顺序不等于多次引擎运行。本例三个事件均标 v2，不虚构先前版本。
- 首页颜色采用最近 collision 的 scope，新增印证不改色；“本次认知变化”仍采用现有 overview.changes，历史火花存在不代表本次又有突破。
- “N 场参与碰撞 / M 条引用”只计算最近 collision 的场次和去重引用，不包含后来单纯认可的场次，不等于独立客户数或证据强度。
- 当前判断被人工修改后保留已有路径作为来源记录，不把旧事件末尾的判断冒充最新人工判断。引擎后续若产生新的认知变化，再追加事件。
- 本版是同一关注点的线性来源路径；多个候选判断的分支仍在现有分歧区展示，不擅自合并。
- 本次未改变导出模块。导出这组新增来源信息需导出负责人另行接入；既有报告仍保留 ABCDV 和证据。

## 双方待确认与联调验收

| 编号 | 待确认 / 验收事项 |
| --- | --- |
| S01 | 场次 ID 从哪里产生？由导入窗口提供，还是现有来源系统提供？谁核对分组？ |
| S02 | 引擎是否按此可选结构返回总览、详情，并补齐路径引用？ |
| S03 | 多份材料同一场次只能显示单场；合并转写如何拆分？ |
| S04 | 多场重复说法只记 corroboration；跨场必须能解释新的条件、反驳或框架变化。 |
| S05 | 事件 ID 与场次 ID 如何跨快照保持稳定、事件如何持久化？ |
| S06 | 旧版本不借未来信息；缺字段、场次冲突、错引用时只降级来源区域。 |
| S07 | 人工纠错后旧路径与当前判断并存的语义是否一致？ |
| S08 | 原文引用真实对齐，历史、分歧、纠错流程仍可使用。 |
| S09 | 来源路径是否进入导出？由导出负责人确认排期与格式。 |

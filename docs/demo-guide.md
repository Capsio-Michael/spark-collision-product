# 智慧火花碰撞｜前端与用例 Demo 指南

交接对象：Michael 与一鸣。日期：2026-10-17。**这是今天的演示内容与页面指导，不是已完成的产品验收声明。** 合成用例在 [`demo/scenarios/design-review/`](../demo/scenarios/design-review/README.md)，口播在 [演示脚本](demo-script.md)。仓库里原有销售报价官网、PPT 仍是独立静态概念演示；这份新指南以设计师和企业客户的日常工作沟通为本轮目标，不把两套案例说成已统一。

## 一句话与范围

用户上传一场企业工作会议的 TXT/Markdown 记录。系统在会议内把具体主张与追问、质疑、补充、反例、澄清、修正、认同的关系连起来，形成零条或多条有原文依据的智慧火花。后续会议继续补证、限定或修正已有洞察，让人看见客户在**具体工作场景**中的关注点和评价标准。洞察如何使用，由用户决定；本次不做任务分派、决策推进、结果保证或自动对外行动。

真实使用可能输入 30–120 分钟的录音纪要或逐字稿，但今天只确认 **TXT/MD 手动上传**。本例 M1 为 78 轮、约 4,000 汉字，M2 为 28 轮、约 1,500 汉字；两者均是**合成文字，不是 30 分钟录音或真实转写**。飞书与其他智能体直接上传是接入方向，尚未验证接通，不在今天页面上表示已可使用。

内容标注和交互关系分开：内容可为发言中的事实陈述、观点、案例、条件；关系必须指向具体主张，支持追问、回应、质疑、补充、反例、澄清、修正、明确认同或条件认同。文本能证明措辞和上下文，不能凭文本推断音频语气、情绪、人格或隐秘动机。发言中的事实陈述只是“他这样说过”；AI 的归纳与原话、报告转述分开。未提及不等于不关注，重复不等于新火花，频次不等于共识；重要性可以解释依据，现有演示评分不得冒充已验证标准。

## 前台一个入口，后台完整管理

主流程固定为 **上传会议资料 → 洞察 Dashboard → 洞察详情 → 多轮交互与原文证据**。入口只保留一个醒目的“上传资料”；TXT/MD 与粘贴记录可在这个入口内选择。不要前置角色配置、场景选择、分析模式、提示词或多个功能入口。用户可稍后在管理区查看来源资料和处理状态、洞察总览、详情、交互标注、证据追溯及跨会演变。入口简单不等于后台只有一张结果页。

| 屏幕 | 首屏必见 | 点击后展开 | 本例展示 |
| --- | --- | --- | --- |
| 上传 | 单一上传按钮、支持 TXT/MD、合成材料提示、小青蛙默认形象 | 材料列表和实际处理状态；选中小青蛙才显示外观选项 | M1 文件先进入，M2 后进入；若走预制内容 fixture，明确写“预置合成标注演示” |
| Dashboard | 2 张轻量洞察卡＋1 条待验证线索、适用场景、变化提示、可点来源数 | 来源材料/状态、历史版本入口、筛选 | 主卡是“克制且有真实依据的专业感”；第二卡为“案例需要现场条件”；两卡不能硬合并 |
| 洞察详情 | 当前理解、范围/条件、形成与后来修正的短时间线 | M1 与 M2 分场展开、原话/转述/预写推断标签、没有批准上线的边界 | M1 中多轮形成；M2 说明展会专题可更鲜明，保留“依据可查” |
| 多轮交互与原文 | 来源会议、P/Q 段落号、发言者、逐字引文 | 点关系连到被回应的具体主张；点引文定位整段原文 | 如 P002→P003→P004→P010→P028→P029→P063→P064；跨场 Q003→Q005→Q023 |

Dashboard 只放能帮助判断“值得看哪条”的信息；关系网络、完整原文、证据缺口放到详情后面。M1 单场已有主洞察，M2 是场景限定和补证，不靠累计次数制造一条新结论。首次展示 M1 结果、随后加入 M2 的前后版本可以用**内部演示回退**切换，但入口仍是一个上传；切换控件写明“合成预置结果”，不演假 AI 等待。预置 fixture 的 JSON 是内容示意，**不是现有 API 返回体**。

## 小青蛙组件要求

原创卡通小青蛙暂称 **Sparky**，默认直接显示，作为友好的分析助手形象。可用文案“交给 Sparky，发现交流中的智慧火花”；产品仍叫“智慧火花碰撞”，本助手小涛不改名。Sparky 是演示命名，未做商标或独占性核查。点形象才展开紧凑的外观选择。可选 2 种样式（圆润、像素）与 4 种配色。外观是个人偏好，**不改变分析模式或输出**，也不是上传前的必经步骤。阅读、思考、发现火花、完成四种状态须绑定真实资料处理状态；演示页手动切换状态时必须写“动效样例”，不能假冒实时 AI 进度。Dashboard 用小尺寸形象，证据阅读时缩到角落或静止，避免大动画遮挡原文。

可复用的 [独立预览](../demo/frog-preview/index.html) 放在本分支，供一鸣复制 SVG/CSS/状态映射；它不是一鸣工作台的正式集成。默认色、四种颜色变量和状态对照见预览目录的 README。不要依据没有提供的“小涛”头像去复刻个人形象。

## 内容 fixture 到页面的映射

`insights-annotations.fixture.json` 用 `M1/M2` 标会议，用 `P001`–`P078`、`Q001`–`Q028` 标原文段落，用 `claim_id` 标可被回应的具体主张。一个标注同时给出 `content_type` 和可为空的 `relation`；关系非空时 `target_claim_id` 指向已有主张。前端展示关系时要让用户同时看到两端原话，不能只画一条没有语义的线。

如果未来接入 v0.1 服务，先把段落定位映射到服务端实际返回的 `record_id/segment_id` 并逐字验证 `quote`；不要把 P/Q 编号硬当现有 API 的 `segment_id`。目前这份 JSON 没有 v0.1 响应的 `data/request_id` 等结构，也没有由现有引擎生成的证据 ID。它只适合预置内容展示或转成**明确标注的**静态原型；正式接口字段须两人共同确认后再接。

## 两人建议分工

| 负责人 | 本轮建议交付 | 交界处 |
| --- | --- | --- |
| Michael：产品/认知质量、引擎与服务 | 确认 M1/M2 的范围、洞察表述和引用；保持 `mock`/真实分析区分；定义内容标注、关系端点、跨会版本需要的数据；决定哪些能力进入以后引擎 | 将本目录的内容 fixture 交给一鸣，接口字段需双方复核后再接 |
| 一鸣：交互与体验 | 一个上传入口；清楚的 Dashboard；洞察详情和逐字证据跳转；前后版本演示；小青蛙可选外观的轻量集成 | 明确标出哪些页面使用预置标注，哪些通过现有 API；不把 fixture 当服务响应 |
| 双方共同 | 同一套 M1/M2 文本、引用和口播彩排；对照验收表勾选实测结果 | 合入或发布之前确认真实浏览器路径和失败退路 |

以上是建议分工，不代表每项已认领或完成。新增帮手可优先检查引文、体验和口播，不临时扩大工程范围。

## 今日最小可演示版与后续

**今日演示目标：**用完整 M1 合成稿展示会议内多轮关系如何形成一条洞察；展开一条独立的案例条件洞察；加入 M2 展示场景限定、重复补证与历史保留；每条引用可定位到 P/Q 段落；页面始终标明“合成/预置标注”或 `mock`。若预置内容还未接入浏览器，使用稿件和标注图讲解，不演成现场自动分析。

**已核实代码边界：**一鸣此前的前端有 91 项测试；本机 API/SQLite 的报价合成 mock 引擎有 5 项服务测试并可导出。两者**尚未用本设计评审案例完成端到端联调**，真实 AI 未接。该引擎只识别原先冻结的报价案例精确原话，本目录的设计评审 JSON 不是其响应；直接上传本稿不会自动得到这里写的洞察。纠错保存返回 501，同场多材料不支持。现有静态官网也是独立预设案例。以上不能在讲解时统称“已实现”。

**后续项：**真实会议长文本抽取与证据校验；会议内关系到跨会版本的正式数据契约；实际音频及有依据的语气标注；飞书/其他智能体接入；真正可保存的纠错；同场多材料归并；正式评分校准。没有任何一项是今天演示的既成事实。

## 彩排验收清单

- [ ] 从唯一“上传资料”入口进入，接受 TXT/MD；M1/M2 均带合成标识；飞书/智能体仅作为未来方向说明。
- [ ] M1 单场结果能指出至少一条洞察如何由多个回合形成；无依据处允许无火花，不把所有话题揉成一条。
- [ ] Dashboard 可看清主洞察、案例条件洞察和待验证线索；重要性依据与共识、批准分开。
- [ ] 展开主卡能看见 P002、P004、P010、P028、P029、P063、P064 之间的具体关系与条件认同。
- [ ] 每条展示的引文逐字出现在标定的 M1/M2 段落；点引用能到原文，返回详情仍保留所在位置。
- [ ] 加入 M2 后保留 M1 历史，显示展会专题的例外条件；Q003/Q023 纠正过度概括，Q022 等只是补证，不伪造新突破。
- [ ] “认可当前设计理解”不显示为批准发布；没有音频时不显示语气、情绪或人格判断。
- [ ] 页面状态标签准确：预置标注写预置，mock 写 mock；无真分析时不播放伪装的实时等待。
- [ ] 小青蛙默认可见，点开才选外观；状态演示与真实处理状态区分；不挡原文。
- [ ] 3 分钟和 90 秒脚本各彩排一次，确认具体点击点可用；失败时按脚本退回可核实稿件。

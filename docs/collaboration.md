## 协作原则

先共同确认 P0 案例、数据结构和服务接口，再分头开发。接口至少约定：稳定的项目/会议/记录/片段/智慧点/会议内标注/跨会议关联/判断版本 ID；片段原文与定位；证据类型及主动提起/被问回应；适用条件；按会议去重的计数、评分规则版本及分项、独立的趋同状态；导入处理中、成功、证据不足、关键冲突和失败状态。具体协议与技术栈由两人确认，不在定义文档里假定已实现。每次合并前用对应验收场景检查，发现无依据结论要降级或删去。新增贡献者从案例、测试、演示切入；扩大工程范围应先看是否影响 17:30 提交。对外表述只能说已验证的功能，不能把文档目标说成产品现状。

## 对现有接口评审稿的变更建议

开发同学的接口契约 v0.1 已有引擎侧评审，尚未冻结。此次范围变化需要双方补齐以下字段与语义，再同步合成 JSON 样例：

1. 导入记录必须归属稳定的 `meeting_id`；同一会议可有多份记录，统计时按会议去重。
2. 会议内标注包含 `meeting_id`、`span_id`、`spark_id`、关系类型、条件与发言者；跨会议关联保存两端标注 ID、关联理由及条件分支，不替换原始标注。
3. 首页与详情分别返回 `distinct_meeting_count`、`total_meeting_count`、可去重的发言者数、主动/被问计数、评分规则版本与分项，以及独立的趋同状态。未知身份与未讨论保持“未知”。
4. 新增会议后返回新旧评分及判断版本；`no_new_insight` 可与会议覆盖增加同时发生。高分不自动升级为“已趋同”或“已批准行动”。

字段名只是供对接讨论的建议，不表示服务已实现或原契约已经修改。

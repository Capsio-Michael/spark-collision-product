# 接口契约 v0.1 评审意见（引擎侧，待双方确认）

来源：开发同学提供的 `api-contract.md`（2026-10-17 评审稿）。本文件只评审建议，不将附件当成已冻结接口，也不表示任何接口已经实现。原稿尚未提交到本仓库；以下按用户已明确的产品目标与分工核对。

## 分工表述

附件开头写“伙伴负责引擎，自己负责交互及接口文档”。按起草者为交互方的视角理解，这与本项目用户提出的分工一致：**用户负责后端引擎与整个服务，开发同事负责交互与用户体验**。为避免两边阅读时“自己／伙伴／用户”的指代变化，后续共享契约统一使用“引擎方”“交互方”。接口文档由谁维护可由双方确认；两个工作室的正式身份仍未确认。

## 可直接保留的共同原则

- 单项目、合成或获准材料、本地持久化、可读导出；原文定位与判断历史不可丢。
- 事实、他人观点、AI 推断和已批准行动分开；认同不推导行动批准；本版不执行外部任务。
- 引文必须匹配真实原文，条件不同不能无条件合并；新证据不能静默覆盖已确认判断。
- 主动提起、被问回应、去重人数、讨论覆盖与未知情况分开；未提及不等于不感兴趣。
- 无新信息或证据不足是合法结果；模拟结果必须标明 mock，不能当作 live 分析通过。
- 服务仅本机监听时可先无登录；模型密钥不进前端，原文和模型输出按安全文本渲染。

## 建议调整与延期

1. **收窄首日接口**：附件定义了 13 个路由和较多快照、幂等、错误状态。完整设计有价值，但今天以 A1–A7 的纵向闭环为优先；先冻结真实会被页面调用的路由与字段，其他保留在后续契约。完整 OpenAPI、24 小时持久化幂等缓存、复杂并发恢复可以后续补齐；若演示确实需要重试保护，先实现同一请求不产生重复分析的最小机制。
2. **补足纠错范围**：附件的 `POST /corrections` 只覆盖判断和条件。产品承诺“使用时纠错”；若用户指出误引或归属错误，界面至少能记录待修复问题并阻止继续把该证据当成可靠结论。是否在 MVP 内直接编辑证据，须双方明确。
3. **无依据推断不能上首页**：附件允许没有证据的 inference/hypothesis 以缺口说明存在。可以把它作为“待验证问题”，但不应显示为已发现的关注点、隐藏动机或认知突破。关键结论仍需可点开的依据。
4. **参与者去重保留未知**：附件要求交互方提供参与者 ID。短记录若没有明确身份，允许未知并从可去重人数中排除；不能仅凭同名跨记录合并。同事确认输入体验，引擎确认统计规则。
5. **历史展示语义清晰**：附件历史总览同时有旧版 `snapshot_version` 和当前 `project.current_version`，`unanalyzed_record_ids` 又按最新版计算。前端要分别标注“所看历史版本”和“项目当前状态”，避免把未来材料混进旧版结论或导出。
6. **演示可重跑**：附件限定唯一项目且无删除/重置接口。测试需要可重复的合成案例；双方约定本地开发数据重建办法，避免把临时重置能力误当用户功能。

## 下一步决定

双方先确认分工表述、异步分析是否采用、最小路由/响应样例、纠错边界和本地联调地址。确认后由负责维护契约的一方提交修订稿；引擎与交互各自在工作分支实现，按 [MVP 验收](mvp-acceptance.md) 联调。当前不冻结附件原稿，也不把本评审意见当成已实施服务。
